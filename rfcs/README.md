# RFC 流程

> 设计总纲 §1：`rfcs/` 收录"改动 `spec/` 或第 0 节四承诺"的提案。

## 什么改动必须走 RFC

以下改动**必须**先写 RFC 并评审通过，才能合入：

1. 改动 `spec/` 下任何文件的**规范性内容**（MUST / SHOULD、线协议、
   错误码、API 路径与行为、事件 schema、扩展点签名与稳定级别）。
   纯文字澄清、 typo 修复、新增非规范性示例除外。
2. 触及 §0 四个承诺（P1 同账号同出口 IP、P2 热路径纪律、P3 单二进制零依赖、
   P4 两步可用）的任何改动——无论是否改 `spec/`。
3. `stable` 级别扩展接口的破坏性变更（必须跨大版本，见 `spec/ext-abi.md`）。

不属于上述的改动（实现细节、内部重构、文档润色）走常规代码评审，
不需要 RFC。

## 流程

1. 在 `rfcs/` 下新建 `NNNN-标题.md`（编号递增，见下模板）。
   状态从 `草案` 开始。
2. 公示评审：至少一名维护者 + 一名受影响的生态方（如 SDK 维护者）参与。
   评审期不少于 3 天（紧急安全修复除外）。
3. 结论三选一：`已接受` / `已拒绝` / `已撤回`，由维护者记录在文件头，
   并附决策日期与理由摘要。
4. `已接受` 的 RFC 必须同步更新 `spec/`（spec-first：契约先行），
   并在对应 spec 文件头标注状态变更。
5. `已拒绝` / `已撤回` 的 RFC 保留归档，不删除（决策可追溯）。

## 模板

```markdown
# RFC-NNNN：标题

- 状态：草案 | 已接受 | 已拒绝 | 已撤回
- 作者：
- 日期：
- 影响范围：spec/identity.md | spec/errors.md | ... | P1/P2/P3/P4

## 背景

（为什么需要这个改动？当前契约/承诺的不足是什么？）

## 提案

（具体的契约变更：改哪些 MUST/SHOULD、哪些字段、哪些映射表。
尽量给出 diff 式的精确描述，而非散文。）

## 兼容性影响

（对现有客户端 / SDK / 替代实现 / 社区 Recipe 的影响；
是否需要大版本、迁移期多久、旧行为保留策略。）

## 放弃的替代方案

（考虑过但不采用的方案及理由。）

## 未决问题

（评审前已知但尚未决定的点。）
```
