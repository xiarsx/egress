# ADR-002：spec-first（先写契约，再写代码）

- 状态：已接受
- 日期：2026-10-17
- 相关：设计 §1、§14；`spec/openapi.yaml`、`spec/vectors/`

## 背景

egress 的价值一半在生态：第三方 SDK、替代实现、社区 Recipe、
外部 Sink 与分析工具都要依赖稳定的契约（身份线协议、错误码、
控制面 API、事件 schema）。如果契约是从代码里"长出来"的，
一次重构就可能悄悄打破所有外部客户端，而无人察觉。

参考项目 Resin 的 DESIGN.md 约一半内容是对外契约、一半是实现细节，
混在一起导致"改实现"与"改契约"无法区分。

## 决策

1. **spec-first**：`spec/openapi.yaml` 手写并评审，代码由它生成，
   反过来不行。字段级契约只住在 `spec/`，实现细节住在代码，
   单项决策住在 `docs/adr/`。
2. **conformance 测试向量**：原文档中的身份解析例子表、健康迁移表、
   P2C 打分例子、错误场景表直接成为 `spec/vectors/*.yaml`。
   第三方 SDK 或替代实现跑通向量即可自证兼容。
3. spec 先发布为 `v0`；至少一个外部 SDK 跑通 conformance 之后，
   冻结为 `v1`。
4. 改 `spec/` 或 §0 四承诺的改动必须走 RFC（见 `rfcs/README.md`）。

## 放弃的替代方案

| 方案 | 否决理由 |
|---|---|
| 代码生成 OpenAPI（code-first） | 重构会悄悄打破客户端；契约变更淹没在代码 diff 里，评审看不见 |
| 删除契约级文档（"代码即文档"） | 外部生态无从依赖；替代实现没有"正确"的定义 |

## 后果

- 正面：契约变更显式、可评审、可版本化（spec 逐项 semver）；
  生态有稳定的测试靶子。
- 负面：前期写 spec 比写代码慢；需要维护"spec 与实现一致"的纪律
  （conformance 向量 + 生成代码校验）。
- 本 ADR 不规定代码生成工具选型（M3 时确定，TODO）。
